# ONLYOFFICE 项目 Hub 重设计规格

- 日期：2026-07-15
- 状态：视觉方向已确认
- 选定方案：方案 1「文档优先」
- 视觉稿：[onlyoffice-hub-design.png](../../assets/onlyoffice-hub-design.png)

## 1. 目标

把当前仓库从“能够运行的演示代码”升级为一个容易理解、容易部署、容易验证、容易二次接入的 ONLYOFFICE 学习项目。升级范围包含三个相互连接的入口：

1. GitHub README：说明项目是什么、能做什么、怎样快速开始，以及下一步应阅读哪份文档。
2. 文档中心：把 Windows、Linux、Docker、后端安装、前端 Docs API 接入和排错内容组织成可连续阅读的教程。
3. 在线演示应用：保留现有 Word/Excel 文件闭环，并增加搜索、筛选、排序、视图切换和更清楚的新手引导。

本次借鉴 Casdoor 的完整产品链路，而不是 GitHub 外壳：README 负责分流，文档站负责深入讲解，演示应用负责证明功能真实可用。

## 2. 范围与边界

### 2.1 本次实现

- README 的项目定位、真实徽章、截图、目录、快速开始、功能矩阵、架构、文档地图、安全边界、FAQ、路线图与贡献入口。
- 本地可访问的文档中心，带全局导航、左侧分组目录、正文、右侧页内目录、提示/警告块和前后篇导航。
- 文档工作台的搜索、Word/Excel 类型筛选、更新时间排序、列表/卡片视图、最近文档、拖拽上传、清晰空状态和移动端适配。
- README、文档中心和演示应用之间的互相跳转。
- 现有创建、上传、打开、编辑、保存回调、下载和删除功能继续工作。

### 2.2 不在本次范围

- 登录、用户和权限系统。
- 多人协作状态、评论、版本历史和回收站。
- 收藏、标签持久化、存储配额统计和管理分析图表。
- 没有真实部署支撑的“在线服务”、下载量或社区规模数据。

界面不得展示无法实际操作的入口。视觉稿中若出现上述概念，实现时必须删除或替换为真实能力。

## 3. 视觉与交互原则

- 延续当前项目的白色、浅灰和深绿色，不复制 Casdoor 的紫色品牌或深色文档主题。
- README、文档中心和演示应用共用一致的项目名称、绿色主色、链接命名和图标语义。
- README“文档导航”使用已确认的快速开始图标：眼睛表示先看效果，Windows 标志表示 Windows，Linux 企鹅表示 Linux，电脑表示 Docker，本地代码符号表示前端接入。
- 图标使用 Lucide 与 Simple Icons 的原始开源资产，不手绘或用字符代替；选中的 SVG 存放在 `public/assets/icons/`，来源与许可证记录在第三方声明中。
- 正文优先使用清楚的标题、短段落、步骤、表格、截图和提示块，避免堆叠代码。
- 桌面端以 1440–1536 像素宽为主要验收尺寸；移动端以 375 像素宽验证可读性和可操作性。

## 4. 信息架构

### 4.1 README

README 依次包含：

1. 项目名称、一句话定位和真实状态徽章。
2. 主要入口：运行演示、快速开始、Windows、Linux、前端接入。
3. Word 与 Excel 的真实截图。
4. 三步快速开始与访问地址。
5. 已支持/不支持的功能矩阵。
6. 浏览器、Node/Express、Document Server 和本地存储的数据流。
7. 文档地图。
8. 安全边界、常见问题、路线图、贡献和许可证。

README 只保留最短可执行命令；生产部署、环境差异和排错全部链接到详细文档。

### 4.2 文档中心

文档中心按用户任务分组：

- 新手入门：项目介绍、快速开始、演示操作。
- Windows：环境准备、启动、验证、常见问题。
- Linux：环境准备、Docker 部署、生产配置、验证与回滚。
- Docker：Compose 说明、环境变量、卷、端口和健康检查。
- 后端：Document Server 与 Node 应用安装、JWT、回调、反向代理。
- 前端接入：Docs API 脚本、编辑器配置、document key、callbackUrl 和保存流程。
- 运维排错：端口、跨域、Mixed Content、JWT、回调、权限、日志和备份恢复。

每篇部署文档统一采用：适用场景 → 前置条件 → 操作步骤 → 预期结果 → 验证命令 → 安全提醒 → 回滚 → 常见问题。

### 4.3 演示应用

首屏结构：

1. 顶部项目身份、服务状态、文档和 GitHub 入口。
2. 新建 Word、新建 Excel、上传、搜索、筛选、排序和视图切换工具栏。
3. 最近文档区域。
4. 全部文档列表或卡片视图。
5. 空文件库、无搜索结果、上传中、服务异常等明确状态。

保留现有文件操作：打开、下载、删除。删除继续使用确认对话框，不增加批量删除。

## 5. 技术设计

### 5.1 文档中心

- 新增受控的文档目录映射，只允许访问仓库中明确列出的 Markdown 文件，禁止使用用户输入拼接任意文件路径。
- 服务端使用 `markdown-it`，配置 `html: false`，生成安全正文和标题目录。
- 新增 `GET /api/guides` 与 `GET /api/guides/:slug`；`/guides` 和 `/guides/:slug` 使用同一文档页面外壳，根据 slug 加载正文、目录和前后篇信息。
- 未知 slug 返回 404 页面和“返回文档首页”入口。
- 文档元数据集中维护标题、分组、顺序、摘要和源文件路径，避免在多个页面重复硬编码。

### 5.2 演示应用

- 文件列表仍以现有 `/api/files` 为唯一数据源。
- 搜索、类型筛选、排序、最近文档和列表/卡片切换在浏览器端完成，不改变文件 API。
- 视图偏好存入 `localStorage`；文件和用户数据不写入浏览器持久存储。
- 拖拽上传复用现有上传接口和大小/扩展名校验。
- 文档打开、保存回调、下载和删除继续复用现有服务，不改变 ONLYOFFICE editor config 合同。

### 5.3 数据流

1. 浏览器读取 `/api/files`，在客户端派生搜索、筛选、排序和最近文档视图。
2. 创建或上传文件后刷新同一数据源。
3. 打开文件时获取现有编辑器配置并加载 ONLYOFFICE Docs API。
4. Document Server 通过现有内部 URL 读取文件，并通过回调保存更新后的内容。
5. 文档中心只读取仓库内受控 Markdown，不访问上传目录。

## 6. 错误处理

- Document Server 未就绪：顶部显示可理解的异常状态，并链接到对应排错章节；文件浏览仍可使用，编辑按钮说明不可用原因。
- 搜索无结果：显示清除搜索和切回全部类型的操作。
- 上传失败：保留服务端错误原因，分别提示格式、大小、压缩包风险和网络错误。
- 文档页面不存在：返回 404，不回退到任意本地文件。
- 文档渲染失败：记录服务端日志，页面显示源文档链接和重试入口。
- 删除失败：保留当前文件行，不提前从界面移除。

## 7. 测试与验证

### 7.1 自动化测试

- 文档目录只暴露允许的 slug，路径穿越输入返回 404。
- Markdown 渲染关闭原始 HTML，并正确生成标题目录。
- 文档清单顺序、分组和前后篇关系稳定。
- 搜索、类型筛选、排序、最近文档和视图偏好使用可独立测试的纯函数。
- 现有创建、上传、读取、回调保存、下载和删除测试继续通过。
- `npm test` 与覆盖率检查通过。

### 7.2 集成与人工验收

- `docker compose config` 可解析，服务健康检查通过。
- 从空库完成：新建 Word → 编辑 → 保存 → 下载 → 删除。
- 从空库完成：新建 Excel → 编辑 → 保存 → 下载 → 删除。
- 拖拽上传 `.docx` 和 `.xlsx` 后可搜索、筛选、排序和打开。
- README 和文档中心的内部链接无断链。
- 1536×1024、1024×768 和 375×812 下无横向溢出、裁切或不可点击控件。
- 用同一尺寸并排比较确认视觉稿与实现，检查间距、字号、边框、圆角、图标和空状态。

## 8. 完成标准

- 新用户可从 README 在五分钟内找到并完成本地启动。
- Windows 和 Linux 用户都能按文档完成部署并验证服务。
- 前端开发者能理解 Docs API、编辑器配置和保存回调的完整链路。
- 演示应用中的所有可见控件都可操作，没有伪功能。
- Word 和 Excel 的真实文件闭环保持通过。
- 主分支测试通过，修改提交并推送到 GitHub。
